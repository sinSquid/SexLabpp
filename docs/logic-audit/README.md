## 验收标准

1. 每个函数、事件、lambda 和 Papyrus native 声明单独建档；自动枚举不等于已审查。
2. 阅读实现，检查边界、失败返回、状态变化、所有权、同步和复杂度。
3. 核对上游输入约束与下游调用契约；有疑点必须明确保留。
4. 确认的错误先复现再修复；优化必须说明行为等价性与资源消耗变化。
5. 可移植测试、源码检查、真实 DLL/VM/游戏验证分别记录。
6. 待审条目清零、解析遗漏对账完成、确认错误处理完毕后，才能称为本轮源码审查完成。无法在本地验证的集成假设单列，不伪装成通过。

## 台账文件

- `inventory.json`：每个生产文件、函数位置、函数源码 SHA-256、状态及结论。
- `decisions.json`：源码阅读检查记录，按函数 ID 与源码指纹绑定，逐项写明验证限制。
- `decision-renumbering.json`：1226条同路径、同名、同本体SHA且checks一致的旧记录迁移证据；不新增通过结论。
- `file-notes.json`：已读文件的检查重点和未闭环问题，不是整文件验证证书。
- `status.md`：自动生成的文件覆盖与解析异常汇总。
- `parser-reconciliation.json`：11个解析异常文件的人工定义对账；按文件SHA、诊断和函数范围校验，改动失效。
- `validation/`：本轮最终可移植测试与sanitizer日志。
- `findings.md`：本轮已修复项目、证据与开放疑点。

`pending` 表示缺少当前位置及指纹匹配的逐函数结论；不能由此推断文件本体未读取。`body_read_this_pass` 来自本轮文件阅读记录与当前指纹匹配，不表示逐函数全链通过。`source_reviewed` 仅表示已阅读实现并记录检查重点。`call_chain_closed: false` 明确表示仍不能宣称调用链全部闭环。测试通过也不自动把其所在文件的全部函数标成已验证。

重建清单：

使用 Python 3.12 和锁定的解析器版本。函数本体指纹不同或位置 ID 不匹配时，旧记录不再应用。该机制不自动证明未修改调用方与已修改依赖仍然兼容；跨文件语义变化仍需人工回查。

当前解析器仍有 MSVC 扩展、宏和 C++ 语法恢复诊断。11个诊断文件已人工对账，当前未发现遗漏的函数定义；保留诊断，不为压低数字改引擎ABI。条目分母包括函数定义、lambda、事件与Papyrus native声明；C++纯virtual/前置声明作为调用契约阅读，不作为实现计数。
